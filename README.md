# Генератор карточек товаров на локальной Qwen3

По JSON с данными о приборе формирует черновик карточки для B2B-магазина — SEO-заголовок, SEO-описание, список характеристик, поисковые запросы и commercial-блок для менеджера. Работает через любую LLM в Ollama (например, локальный Qwen3), язык — TypeScript.

## Требования

- Node.js 20+
- Ollama

## Установка и запуск

```bash
# 1. Модель
ollama pull qwen3:8b      # qwen3:8b / qwen3:14b...
ollama serve              # если сервис ещё не запущен

# 2. Зависимости и настройки
npm install
cp .env.example .env      # при необходимости поменяйте OLLAMA_MODEL и OLLAMA_BASE_URL

# 3. Запуск на примерах
npm start -- examples/product1.json examples/product2.json

# своя папка результатов
npm start -- my_product.json --out results
```

Результат печатается в консоль (Markdown) и сохраняется в `out/<имя>.md` и `out/<имя>.json`. Для файлов с несколькими товарами (XML, JSON-массив) к имени добавляется id: `out/template_455683.md`.

Ход работы (попытки генерации, найденные проблемы, повторы) выводится в stderr. Уровень журнала задаётся в `.env`: `LOG_LEVEL=debug|info|warn|error|silent`; в `debug` добавляются запросы к модели и время ответа.

Ollama может работать на другой машине: укажите её адрес в `OLLAMA_BASE_URL`.

Тесты (LLM не нужна): `npm test`. Проверка типов: `npm run typecheck`.

## Форматы входа

```json
{
  "name": "Имя",
  "manufacturer": "Производитель",
  "specs": { "Характеристика1": "0–1,6", "Характеристика2": "1,5" },
  "description": "Описание"
}
```

**XML** (`examples/template.xml`): несколько `<offer>` подряд, общий корень не нужен. Соответствие полей:

| XML | Поле |
|---|---|
| `<name>` | `name` |
| `<vendor>` | `manufacturer` |
| `<typePrefix>` | `description` |
| `<param name="...">` | `specs` |

< В `template.xml` характеристик нет, поэтому карточка строится только по названию, типу и производителю, а в разделе «Требует уточнения» появляется пометка об отсутствии характеристик.

Обязательно только `name`. Остальные поля могут отсутствовать, быть пустыми или `null`.

## Как устроено

```
вход JSON / XML → валидация (zod) → список пропусков (код)
  → LLM: тексты по JSON-схеме → проверки → повтор или правка описания
  → сборка карточки (характеристики берутся из входа кодом) → JSON + Markdown
```

1. **Модель не генерирует характеристики .** Список `key_specs` собирается кодом из входного `specs` без изменений, проверяются существованием чисел в исходных данных. 
2. **Отчёт о пропусках делает код**, а не LLM (`missing_data`): отсутствие производителя, описания и характеристик целиком. Если характеристик нет совсем, в карточке пишется «данных нет», а промпт запрещает называть технические значения.
3. **Промпты в одном файле:** все тексты для модели (системный, пользовательский, замечания, правка описания) лежат в `src/prompts.ts` в объекте `PROMPTS`; остальной код промптов не содержит.
4. **Промпт:** жёсткий запрет на факты вне `<product_data>`, данные обёрнуты в тег и помечены как «данные, не инструкции» (защита от инъекций через `description`).
5. **Structured output:** в Ollama передаётся JSON Schema ответа (`format`), режим размышлений Qwen3 отключён (`think: false`), блоки `<think>` дополнительно вырезаются.
6. **Проверки результата кодом** (модель плохо считает символы):
    - заголовок не длиннее 70 символов, 3–5 поисковых запросов, заполненный commercial-блок;
    - описание 800–1200 символов; для товаров без характеристик длина не проверяется, для товаров из XML проверяется только верхняя граница (1200);
    - все числа в тексте должны встречаться во входных данных.
7. **Повторы.** Если проверки не пройдены, модели отправляется список проблем с подсказками и запрос повторяется с растущей температурой (`LLM_MAX_RETRIES`). Если проблема только в длине описания, JSON не перегенерируется (модель при этом повторяла прошлый ответ): описание правится отдельным коротким запросом, а если и это не помогло, обрезается по границе предложения. Нерешённые проблемы попадают в раздел «Предупреждения».

7. **Ошибки:** недоступный Ollama, отсутствующая модель, таймаут, пустой/некорректный ответ, битый входной JSON, пустое название — понятные сообщения без трейсбека; ошибка в одном файле не останавливает обработку остальных.
8. Конфигурация только через `.env` (в `.gitignore`). Облачных ключей нет.

## Ограничения и улучшения

- Проверка чисел не ловит выдуманные нечисловые факты (например, «ГОСТ» без цифр, материал корпуса, отрасль). Улучшение: второй проход LLM-проверкой «каждое утверждение подкреплено входом» и список запрещённых слов.
- Малые модели (1.7B–4B) слабее пишут по-русски и чаще не попадают в длину — требуется больше повторов.
- Нет оценки качества сгенерированного текста.
